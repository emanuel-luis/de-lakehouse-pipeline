| 11 | 2026-10-25 | Where key uniqueness is tested once bronze exists (PR2) | Only in bronze, for all nine tables; staging keeps not_null, accepted values and ranges. | 12 | 2026-10-25 | What incremental `bronze_orders` does after a full load of orders (PR3) | A pre-hook, only in incremental runs, deletes every row of the table when the ingest log has a successful full-mode `orders` run newer than the table's `max(_batch_id)`; the batch filter then reloads all of landing. Inline in the model, no macro. | A full load replaces the landing directory (for example after the source is regenerated); merging only by `order_id` would keep orders that no longer exist and break the relationship tests. The plan did not cover it. |
